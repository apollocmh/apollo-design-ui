## 三、本轮修掉的 3 个跨包缺陷（都不是 test-utils 引入，但都会让门禁永远红着）

### 1. `lint:types` 在 HEAD 上就是红的（2 个错误）

上一份日志已经定位过，本轮修掉：

- `packages/theme/build.config.ts` —— hook 里手写的解构类型注解把 `getDesignToken` 写成
  `(config?: { algorithm?: unknown; token?: Record<string, unknown> }) => Record<string, unknown>`，
  与 dist 真实签名 `(config?: ThemeConfig) => AliasToken` 不兼容（严格参数逆变下
  `Record<string, unknown>` 不能赋给 `ThemeConfig['token']`）。
  **修法**：删掉整块手写注解，让 TS 从 `dist/index.d.ts` 推断 —— dist 自带类型，注解只会漂移。
- `packages/utils/src/env.ts` —— `ProcessEnvLike`（两个可选属性）是 TS 的 **weak type**，
  而 `process.env` 的真实类型 `NodeJS.ProcessEnv extends Dict<string>` **没有任何具名属性**，
  于是报 TS2559「no properties in common」。
  **修法**：给 `ProcessEnvLike` 加同形状索引签名 `[key: string]: string | undefined`
  （而不是 `as` 断言）。

> 顺带证明：`theme` 的这个错误**会变脸** —— `dist/` 不存在时是 TS2307（模块找不到），
> 构建后才是真正的类型不匹配。所以「先 lint 再 build」和「先 build 再 lint」看到两个错误。

### 2. `scaffold-packages.mjs` 漏声明 test-utils 的两个依赖

`theme-test.ts` 直接复用 `@apollo-design/theme` 的 `ThemeProvider` / `getDesignToken`
（T2），`warnings.ts` 复用 `@apollo-design/utils` 的 `resetWarned`，但脚手架模板的 `deps`
里两个都没有。后果是 **L7 的 B1 失败**：

```
unbuild 退出码 1: Potential implicit dependencies found: @apollo-design/theme
```

unbuild 遇到「被 import 但未声明的 workspace 包」会把它当成**要被内联打包**的目标。
**报错信息说的是「隐式依赖」而不是「缺依赖」**，很容易误读成配置问题。

修法是**两处一起改**（这是本仓库特有的陷阱：`package.json` 由脚手架模板拥有，
手工加的行会在 `scaffold --force-pkg` 时被抹掉）：

1. `registry/tools/scaffold-packages.mjs` 的 test-utils `deps` —— 真正的所有者
2. `packages/test-utils/package.json` + `README.md` 的依赖表
3. `pnpm-lock.yaml` 的 importer 段（workspace link，无网络依赖，可手改）

外加 `packages/test-utils/node_modules/@apollo-design/theme` 符号链接
（`pnpm install` 在本环境会挂起，手工 `ln -s ../../../theme` 与 pnpm 布局一致）。

修完 `deps` 之后 `foundation.json` 的 `dependsOn` / `implOrder` 也才与事实一致 ——
此前 test-utils 被算作**零依赖**，排在 icons 之前，是虚假的拓扑序。

### 3. `--verify` 在本沙箱里跑不起来（环境问题，不是仓库问题）

第一次跑 `--verify` 9 秒就退出、拿不到报告。根因不在仓库：

**这个坑只影响「跑覆盖率」，不影响仓库本身。** 已写进 `MEMORY.md` 的坑列表。

## ⭐ 本轮最重要的三个发现

1. **§3.1 `getPopupContainer` 不需要换算**：antd 测量前把 popup 归零到 `left/top=0`，
   于是 `popupRect.x/y` 就等于**包含块的视口坐标**，容器偏移在
   `targetAlignPoint − popupAlignPoint` 的减法里自动消掉。
   ⇒「坐标系解析」不是换算函数，而是「**必须在归零位置测量**」的不变量。
2. **三条必须照抄 antd 的顺序/判据**（写在契约文档 §6.1，改了就与上游分叉）：
   - placeholder **先 `appendChild` 再读 `offsetLeft`**（插入本身会改变 flex/grid 布局）
   - body/html 跳过用 **`instanceof`**（跨 iframe 时与「语义化写法」行为不同，按规格复刻上游）
   - scale 必须用**归零态**的 computed `width/height`（还原后可用宽度可能不同）
3. **一处有意加强**：antd 没有 `try/finally`，抛异常会把 `left:0/overflow:hidden`
   永久留在 inline style 上。我们用 finally 包住，正常路径行为一致。

## ⭐ 三个必须记住的发现

1. **start 步的样式必须 emit 才上屏**（本轮修掉的真实 bug）。
   antd 是 `setStyle([...])` —— 一个 **setState**，天然触发重渲染；
   我们的 `handlerStyle` 是闭包变量，只赋值不通知任何人。
   少了这次 emit，start 态样式永远不上屏，collapse 会从自然高度直接跳到终态。
   已做变异验证：去掉 `emit()` → 2 个用例失败。
2. **start 步拿不到 element 是 antd 的真实行为，不是 bug**。
   首帧 `styleReady === 'NONE'` ⇒ 组件返回 null ⇒ 那时没有 DOM；
   而 start 步是在 `onMounted` 里**同步**跑的，重渲染要等下一 tick。
   antd 的 collapse 因此只在 **active** 步用 element 测高度。
3. **`detectMotionSupport` 的判据必须基于注入的 win**。
   混用全局 window 会导致 `detectMotionSupport({})` 用 jsdom 的 document 当
   `domSupport` 的依据、又用空对象 createElement，得到 `style === undefined`，
   `styleProp in undefined` 直接抛 TypeError。

## 结论

## 产物

- `use-portal.ts`（~330 行）—— `usePortalContainer` / `usePortalOrder` / `useZIndex`
- `portal.ts` —— `Portal` 组件（`<Teleport>` 封装）
- `mock.ts` —— `portalInlineMock`（`mock.js` 的机械移植）
- `docs/foundation/portal-contract.md`

## ⭐ 三个不写下来就会踩回去的点

1. **首次 append 必须用 `onMounted`，不能用 `watch(..., { immediate: true })`**。
   `immediate` 在 **setup 里同步**跑，而 setup 自顶向下 ⇒ 父级在子级被创建前就
   `append()` 并置 `appended = true`，子级于是认为「父已入 DOM」而立刻自己 append，
   **嵌套顺序反转**。React 的 layout effect 与 Vue 的 `onMounted` 都是自底向上。
2. **`getContainer` 是两层**：选项本身是「取 spec 的 getter」，`GetContainer` 又能是函数。
   少外層 ⇒ 读不到最新 props；少内层 ⇒ `resolveContainer` 拿到 `undefined` 只能给 `null`，
   「未就绪」第三态消失，内容会先渲染进默认容器再搬家。所以 `Portal` 的 prop 收 spec 本体，
   传给 `usePortalContainer` 时才包成 `() => props.getContainer`。
3. **`ZINDEX_KEY` 必须 provide `ComputedRef<number>`**，不能 provide 裸数值 ——
   provide 标量不会让子孙更新。

## 一处照抄的噪音（别优化）

`useDom(mergedRender && !innerContainer)`：`innerContainer === false` 时 `!false` 为真

## ⚠️ 数量是 73，不是 75

早期模板写的「75 个语言包」是错的。实测 antd 6.6.4 的源码（`components/locale/*.ts`

## 事实来源

- **antd 6.6.4 的 ESM 产物** `/tmp/antd-src/package/es/locale/*.js`（不是 TS 源码 —— 产物是干净 ESM）
- `@rc-component/pagination@1.4.0` 与 `@rc-component/picker@1.12.2` 的 `es/locale/*`

⚠️ **antd 不 vendor 这两份 rc 数据**：`es/locale/zh_CN.js:1` 就是
`import Pagination from '@rc-component/pagination/locale/zh_CN'`。
语言包引用了 **134 个**不同的 rc locale 说明符（67 个语言 × 2 个包）。

## ⭐ 生成管线（`registry/tools/gen-locale.mjs`，486 行）

**求值而不是解析**：把三个来源的 ESM 原样拷进临时目录 → 重写 import 说明符 →
`await import()` 真的求值 → 序列化。

为什么不写正则抠对象字面量：语言包**不是纯 JSON** ——
它 import 了 4 个分片（2 个来自 rc 包）、`es_US` 还会 `...esES` 展开另一个语言包、
而且**每个包的 import 集合都不同**（`es_US` 就没有 `Pagination`/`TimePicker` 的 import）。
正则会同时被模板字符串、嵌套对象、以及这个差异击穿。

未知的 import 说明符会**抛错**（不是静默漏掉）—— 上游新增依赖时会立刻发现。

**rc 数据固化**：`--sync-rc` 拉一次 → `registry/source/locale-rc/`（67+67 个文件，548K），
`provenance.json` 记包名 + 锁定版本 + **每个文件的 sha256**。
日常生成与 `--check` 只读固化副本 ⇒ **离线确定**。

**一个语言一个文件**（自包含，19001 行 / 780K）：tree-shaking 天然成立、
不需要跨语言去重（那种启发式会让重新生成不确定）、diff 稳定。

**序列化要保住三件事**：共享引用（`typeTemplate` 抽成局部常量，13 个 `types.*` 指向它）、
键顺序（按插入顺序，否则每次 diff 都很大）、字符串转义（`${label}` 原样保留）。

2. ⚠️ **U 项（跟随的上游缺陷）**：`changeConfirmLocale()` 无参分支只重置 `runtimeLocale`、
   **不清 `localeList`** ⇒ 重置不彻底（之后再注册会把栈里的叠回来）、栈单调增长。
   照抄，另导出测试专用的 `resetConfirmLocale()`。
3. **没有子路径入口**（裁决 A 是单文件产物）⇒ 只能 `import { zh_CN }`。

4. **不引 utils 的告警**：为保住零依赖，`LocaleProvider` 的废弃告警用 10 行本地实现

## ⚠️⚠️ 最大的发现：/tmp 的两个 antd 副本被系统清理了

「事实来源」（AGENTS.md §5.1）。已恢复，方法要记下来：

```bash
# 1) 产物（ESM + 类型 + 样式）—— npm 可用
mkdir -p /tmp/antd-src && cd /tmp/antd-src
npm pack antd@6.6.4 --silent && tar xzf antd-6.6.4.tgz   # → /tmp/antd-src/package/

# 2) 源码 + 测试 + demo —— ⚠️ curl 走了不存在的代理（127.0.0.1:7890）会失败
#    必须用 node 的 fetch（codeload 直连可用）
mkdir -p /tmp/antd-repo && cd /tmp/antd-repo
node -e "fetch('https://codeload.github.com/ant-design/ant-design/tar.gz/refs/tags/6.6.4')
  .then(async r => require('fs').writeFileSync('antd.tar.gz', Buffer.from(await r.arrayBuffer())))"
tar xzf antd.tar.gz && mv ant-design-6.6.4 ant-design-master
```

**不会**把 tarball 解到 `/tmp/antd-src/package/` —— 那一步要手工做。

## empty 的分析结论（摘要，全文见 docs/analysis/empty.md）

- 300 行 / 10 文件 / 6 demo / 6 测试；**无组件依赖**；rc 依赖只有 `isReactRenderable`
- **没有任何用户可覆盖的 Component Token** —— 样式里的 `emptyImgHeight*` 是 antd 的
  **内部 merged token** ⇒ `registry/tokens.json` 的 `tokenStatus` 应记 **`n/a`（附依据）**
- DOM：根 > `-image` / `-description`（按需）/ `-footer`（按需）
- 三条容易写错的判据：
  1. `des` 用 `!== undefined` 判断，**不是**真值判断 ⇒ `description={false}` 会走到
     「用传入值」那一支，再被 `isRenderable` 拦掉。**两条判据不同，别合并**
  2. `alt = typeof des === 'string' ? des : 'empty'` —— 用的是 `des` 不是 `description`
  3. `imageStyle` 与 `styles.image` **合并**，后者赢
- ⚠️ `PRESENTED_IMAGE_*` 在 antd 里是**模块级 VNode 单例**，靠 `===` 驱动 `-normal` 类名。
  **Vue 的 VNode 不能跨渲染复用** ⇒ 我们必须导出**组件**而不是 VNode（PLATFORM 差异）
- `@apollo-design/utils` 里**没有** `isRenderable`（已确认），`theme` 里**没有** `getAsSolidColor`
