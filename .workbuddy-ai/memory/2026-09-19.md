## 1. 主体：`batch3b.test.ts`（95 例）

分五组：`validateRule · 单条规则` / `validateRules · 规则编排` / `Field · 注册与生命周期` /
`Field · getControlled 受控注入` / `Field · 校验` / `Field · shouldUpdate 与 dependencies` /
`Field · preserve 与 refresh` / `Field · 组件契约细节`。

测试基建沿用 ③a：`new FormStore(forceRootUpdate)` + `provide(fieldContextKey, form)` +
`mount(Host)`，host 用 scoped slot 捕获 `(control, meta, form)` 三元，
并自带 `renderCount()`（数 slot 调用次数）与 `createProbe()`（数子组件 mount/unmount）。

### 三次被测试红灯纠正的**契约理解错误**（读源码确实会漏）

1. **`validateRules` 的返回 promise 在并行分支永远 reject** —— 即使全部通过也是
   `reject([])`（`.then(errors => Promise.reject(errors))`）。原以为「全过就 resolve」。
   ⇒ 断言改成 `await expect(...).rejects.toEqual([])`。
2. **`validateFirst === true` 且全过是 `resolve([])`** —— 与并行分支**不对称**。
   这是上游的真实行为（串行分支直接 `resolve([])`），不能「顺手统一」。
3. **`warningOnly` 排序后同组内保持原序** —— 用「记录调用顺序」的串行用例才观察得到；
   早期用 `resolves/rejects` 观察不到顺序，变异 M2（方向反转）当时**差点漏掉**。

### `Field` 的两层结构在测试里怎么观察

| 上游手段 | 测试里怎么观察 |
|---|---|
| `forceUpdate()` | `renderCount()`（slot 被调用的次数）增加 |
| `setState({resetCount})` | `createProbe()` 的 `mounted/unmounted` 计数（keyed Fragment 整体重建） |
| `cloneElement(child, control)` | 断言 `control` 对象本身（`value` / `onChange` / `onBlur`） |
| `componentDidMount` | `getFieldsValue()` 出现该字段 |
| `componentWillUnmount` | 卸载后 `getFieldsValue()` 不含该字段 + `onMetaChange({destroy:true})` |

## 2. 变异验证：24 组，23 杀 + 1 等价

`validate-util.ts` **10/10 全杀**；`field.ts` **13 杀 + 1 等价**。
逐组结果与「首轮存活」的定位过程已写进契约 §4.7.8.2，此处只记**方法论**：

### ⭐ 4 个变异首轮存活 —— 全是真断言缺口，不是「变异无效」

| 变异 | 存活的根因 | 处方 |
|---|---|---|
| **M7**（数组子规则递归去掉 `!result.length` 守卫） | 原用例传 `value = undefined` ⇒ `Array.isArray(undefined)` 直接为假，**守卫根本没被求值**，但该行已记为「覆盖」 | 改成「父规则 `min:5` 与子规则 `required` **都会**报错 + 值是非空数组」⇒ 守卫生效 1 条 / 失效 3 条 |
| **F1**（`requireUpdate` 恒真） | `setFieldValue` 走 `setField` 分支**早退**，`requireUpdate` 从未被求值 | 换入口：有 `dependencies` + 自身值未变 ⇒ 走 `default` 分支 |
| **F8**（`isFieldDirty` 忽略 `initialValue`） | `isFieldDirty()` **不在公开 `FormInstance` 上**，测试找不到入口 | 改从 `validateFields({dirty:true})` 的**过滤行为**观察 + 一个「应被跳过」的对照组 |
| **F14**（`setFields` 的 `errors` 被丢弃） | 原用例只注入 `errors: []`，与 `|| EMPTY_ERRORS` 兜底**等价** | 补「注入非空数组 ⇒ 原样进 meta」+「显式空数组 ⇒ 清空」 |

⭐ **F8 的对照组还顺带抓出了一个真 bug（我的调用写错了）**：
`validateFields(undefined, { dirty: true })` 会落进**无参重载**（`form-store.ts:818-823`
的三个判据全假）⇒ `options` 被丢掉 ⇒ `dirty` 过滤**静默失效**，
对照组字段（本应被跳过）也报了错才发现。改成单参 `validateFields({ dirty: true })`。
→ PITFALLS 79。

### ⛔ 1 个等价变异（F6）—— 不谎报击杀

去掉 `Field.getControlled` 的 `if (rules && rules.length)` 守卫后，`dispatch({type:'validateField'})`
仍会被 **store 侧第二层同名守卫**（`form-store.ts:851`）拦掉 ⇒ `meta` / `onFieldsChange` /
`validateFields` 返回值全部无差异 ⇒ **等价变异**。

处理：补一条锁**行为契约**的用例（「无规则 ⇒ 不产生校验」），
并在测试注释里明写「这不是某一行守卫的证据」。契约 §4.7.8.2 也写明了。
→ PITFALLS 77。

### 变异纪律（照做）

- 每个变异「**应用 → 跑 → 还原 → `shasum -a 256` 比对**」一条命令内完成，绝不并发；
- 备份在 `/tmp/3b-backup/`，还原后必须看到 sha256 与备份一致；
- **失败数要记录**（1 failed / 2 failed / 19 failed …）—— 只记「红了」无法区分

## 4. 顺手删掉的一处死代码

`field.ts` 的 `entityProps` 里原本有 `preserve` / `isListField` / `isList` 三个 getter。
核对 `form-store.ts` 发现：store 只读 `field.props.{rules, dependencies, initialValue}`，
`preserve` / `isListField` / `isList` 走的是**方法**（`entity.isPreserve()` / `isListField()` / `isList()`）
⇒ 三个 getter **永不被读**。删掉（保留就是未覆盖的死代码）。

⭐ 判据：`entityProps` 的注释里原本写「其余字段是为了与 `FieldEntityProps` 的声明对齐」——
但「类型对齐」不构成保留死代码的理由，**接口的其余键是可选的**。
